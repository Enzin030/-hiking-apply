# 03_Schema — 現行系統資料表結構

現行「臺灣登山申請一站式服務網」正式庫的結構落地，由
`01_Raw_Input/現行tableSchema.csv`（機關提供的匯出）規整而來，做法參照 115 嘉市災管的
`03_Schema`。**本資料夾描述的是「現在長什麼樣」，不是「改版後要長什麼樣」**——
新版設計另開檔案，不要就地改寫這裡的結構事實。

## 規模

| 項目 | 數量 |
|---|---|
| 資料表 | 272 |
| 欄位 | 3,535 |
| 有 PK 標記的表 | 174（另 98 表匯出檔未標 PK） |
| 欄位中文名待補 | 1,566（44%） |

狀態分布（**依命名推測**，見下節）：現役 228、系統框架 15、疑似備份 16、檢視 8、疑似暫存 5。

其中 142 張有表中文名（來自 `01_Raw_Input/現行表描述.csv`），130 張留空。

## 檔案結構

| 檔案 | 內容 |
|---|---|
| `<表名>.md` | 一表一份。frontmatter 是統計與狀態，正文寫用途與業務規則（目前多為 `[待確認]`） |
| `_backup/<表名>.md` | 16 張疑似備份表另放一層，**目錄視圖不顯示**，改由「備份表」視圖單獨看 |
| `_fields/<表名>__<欄位名>.md` | 一欄位一筆記，是欄位內容的真源；由 `00_目錄.base` 呈現成表格 |
| `00_目錄.base` | Obsidian Bases 視圖：目錄／現役資料表／疑似停用／備份表／單表結構／所有表結構／待補中文名／外鍵關聯 |

備份表的**欄位筆記仍然平鋪在 `_fields/`**（Bases 靠屬性過濾，不靠資料夾），
每份帶 `表狀態`，欄位層的三個視圖靠它把備份表的欄位濾掉。

## 兩份匯出檔

| 檔案 | 提供什麼 |
|---|---|
| `01_Raw_Input/現行tableSchema.csv` | 欄位層：表名／欄位名／中文名／型別／長度／預設值／可空／PK |
| `01_Raw_Input/現行表描述.csv` | 表層：表中文名（248 筆，其中 142 筆有值，106 筆為 `NULL`） |

描述檔**少收 24 張表**，而那 24 張幾乎全是檢視（`vw_aspnet_*` 六張、`*_view` 七張、
`vw_NCDR_Warning`，以及四張中文名的查詢用表）——這反過來佐證了狀態分類裡的「檢視」。
`描述檔收錄: false` 就是這批。[待確認] 其餘幾張（`C_150`、`bedBookingWaiting`、
`applylist_roadbook` 等）為何不在描述檔裡。

表文件的「## 欄位」段是 `![[00_目錄.base#單表結構]]` 嵌入，靠 frontmatter 的 `Table`
自動過濾出該表欄位，不在 markdown 裡另存一份表格（存兩份就會不同步）。

## 命名一律逐字保留

表名與欄位名（`AI_ID`、`CRTDATE`、`apply_log`、`___filesSizeCount`）**就是現行 DB 的
真實識別字，不做 PascalCase 或 snake_case 轉換**。嘉市災管那邊轉是因為在設計新表名，
這裡轉了只會產生 DB 裡不存在的名字。因此也沒有 `TableSnake`／`FieldSnake` 這類欄位。

## 狀態分類是推測，不是結論

`狀態` 由表名特徵推得（`_bak`、日期數字、年份區間、`tmp`、`aspnet_` 前綴…），
frontmatter 一律標 `狀態來源: "命名推測"`，`狀態依據` 記命中哪條規則。

**不得據此刪表或停用。** 要確認某表是否真的死了，必須查實際使用（程式碼引用、
最後寫入時間、資料筆數），那份查證還沒做。

方向是**寧可漏抓不要錯抓**：被標出來的 44 張逐一看過，沒有誤判；但沒被標到的 228 張
**不代表都活著**，命名看不出來的死表一定還有。這份清單不是停用表的完整盤點。

## 未知資訊留白，不猜

- **欄位中文名** 匯出檔本身就有 1,566 欄是空的，一律留空，不由欄位名反推。
  空白本身就是待辦清單（`00_目錄.base` 的「待補中文名」視圖）。
- **表中文名** 只填描述檔給的那 142 張，其餘 130 張留空。描述檔給的是「描述」不是嚴格的
  名稱（如 `ApplyBanTime` → 「禁止申請時間(抽籤時間)」），照收不改寫。
- **外鍵** 匯出檔沒有外鍵資訊，`外鍵指向` 全部留空。命名上看得出關聯的（如
  `a_id` → `applylist`）也不先填，避免把推測當成已確認的關聯。
- 表用途與業務規則一律 `[待確認]`，待訪談補。

## 重新產生

```
node scripts/gen-schema-from-csv.js --dry-run   # 只報告差異，不寫檔
node scripts/gen-schema-from-csv.js             # 產生／更新
```

產生器是**合併式**，不是重建式：

- CSV 是 DB 事實的真源 → 鍵值／資料型別／長度／預設值／允許空值／`Seq` 一律以 CSV 覆寫，
  與既有值不同時列進差異報告。
- 人工填的 **中文名稱／備註／外鍵指向／資料表中文名** 既有值非空就保留，CSV 洗不掉。
- 表文件的正文（用途說明、內部註記）只要檔案已存在就整段保留，只更新 frontmatter。
  例外是 H1 標題：**還維持產生器原樣**（`# 表名` 或 `# 表名【中文名】`）時會跟著中文名更新，
  人工改過標題就不動。
- 分類改變讓表換了資料夾時，舊位置的正文會被搬到新位置，**舊檔不刪**，只列進報告。
- **不刪任何檔案**。CSV 已無對應的欄位筆記只列進報告，由人工判斷。

機關之後給了新的匯出檔，覆蓋 `01_Raw_Input/現行tableSchema.csv` 再跑一次即可，
`--dry-run` 的差異報告就是「這次改了哪些欄位」。主控台只印前 40 筆，
**完整清單一律落在 `.scratch/outputs/schema-diff-<日期>.md`**。

表文件 frontmatter 的 `中文名待補`／`外鍵數` 是**合併後**的即時統計（不是照 CSV 算），
所以在 Bases 填完中文名或外鍵、重跑一次，目錄視圖的數字就會跟著動。

## 沒有「新增欄位」的工具

Bases 的表格**不能新增列**，所以在 Obsidian 裡沒辦法生出一份新的欄位筆記。
嘉市災管那邊有 `scripts/add-field.js` 補這個洞，這裡**沒有移植**——本資料夾描述的是
現行 DB 的既成事實，欄位由匯出檔決定，不該在文件端憑空長出來。

真的要加（例如匯出檔漏了一欄），手動複製一份 `_fields/<表名>__<欄位名>.md` 改內容，
或補進 CSV 後重跑產生器。後者較好，因為 CSV 是結構事實的真源。
