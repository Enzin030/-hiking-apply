## 5. 三組承載量欄位不是「不知道哪組生效」，是各管不同住宿型態

我在 P6 階段說「三組配對都是活的，哪組生效不明，屬 `[缺口]`」——**明細 A16 已經解開**，

也就是說，本檔第 5 點解開的那組承載量欄位，**它們的值正是由 `bedtype` 分流產生的**。

   code 只是自己前後一致，不等於與資料填寫時的約定一致。
2. `booking_bed.bedtype` 與 `bedlist.bedtype` 是**兩張表的同名欄位**，語意是否相同？

   這代表至少在 `booking_bed` 這張表上，`bedtype` 不承載床／營區分。

**在得到答案前的自保做法**：不要引用任何「床位 X 個、營位 Y 個」的數字；
要判斷某地點是山屋還是營地，改用本檔第 5 點的 `node.roomtype`（0=山屋、1=營地、2=並存），
那個有 `tarokoapplyControl/step2.ascx.cs:728` 的註解與資料分佈雙重佐證。

## 判定四種

| 判定 | 意思 |
|---|---|
| **一致** | code 有對應實作，且行為與原文相符 |
| **不一致** | code 有實作，但條件、數值或範圍與原文不同 |
| **沒實作** | 全樹搜尋後找不到對應實作（不猜） |
| **值在DB(待查)** | code 有實作骨架，但數值來自資料庫欄位；已註明表名欄名 |

## 先講三件影響全表的事

1. **林業署四座山屋（檜谷／天池／嘉明湖・向陽／九九）的規則，大多不由這套系統執行。**

   `tconline_APIURL`／`sendTeamsDataUrl`）。`notice_b1`–`b7` 的申請期限、抽籤、繳費、退費、
   停權條文，判定一律是「**沒實作（外部系統）**」——不是漏做，是不歸這套系統管。
   例外是**九九山莊**：`b7` 原文明寫「請至臺灣登山申請一站式服務網申請」，
   而系統確實有 `App_code/JiujiuHutApi_code/`（9 支）在對接。
2. **人數、期限、承載量的數值全部在 DB**，不在 code。這些列判「值在DB(待查)」，是你要連 DB 補的清單。
3. **`notice_a2`／`a5`／`a8`（三家的「申辦規定與須知」）只有法規名稱清單，沒有可抽取的數值**，
   全表未列。`notice_a3`／`a6`／`a9`（緊急聯絡資訊）與 `a10`（糧食裝備）同理。
4. **「值在DB」的那些值，各有一個後台畫面在設。**
   2026-09-11 起，**規則值 → 後台維護入口**的對照表在
   `2026-09-11-106年操作手冊可用內容.md` §2.4（來源：106 年後台操作手冊）。
   查一個數值「誰在設、在哪設」先看那張表，再決定要不要連 DB。
   注意該手冊已 9 年，**證據位階低於當前截圖與 DB 實測**，它給的是入口與語意，不是現值。

**兩個方向同時成立，不要只記住其中一個：**

1. **系統做的比 code 靜態閱讀所能判斷的多。** 7 列從「沒實作／待查」升格為「一致」，
   最關鍵的是太魯閣三種路線群的申請期限——天數完全資料驅動且與原文相符，
   我原本判「沒實作」是錯的（`Fixedclimb` 有路線層級的 `ParkPeriodDayBef`／`MonthBef`）。
   同樣被推翻的還有：玉山 `ord` 100–1000 是刻意設計不是硬編碼失誤、
   `foreignerresvedplaces` 是活欄位、三組承載量欄位由 `roomtype` 決定而非「不明」。

2. **但「不一致」幾乎翻倍（14 → 25），而且新增的 11 列全部是「不連 DB 就看不出來」的類型。**
   靜態讀 code 只能看到「有讀這個欄位」，看不到欄位裡裝的是什麼：
   玉山雪季人數（原文 6／DB 12）、玉山異動天數（原文 5／DB 7）、
   雪季日期停止維護、2026 春節封園設了但不被讀取、C 類停權不生效、
   9 條路線 `peopleset=1` 卻上下限全 0、觀高與白洋金礦兩筆費用不在任何機關原文。

3. **但 DB 數字也會製造假的「不一致」，反向要防。** 2026-09-08 驗收時把
   「`afterstatus` NULL 上百萬筆」重新查證，結論是**統計口徑不是落差**——
   我原本的 B4 查詢是無條件全表計數，沒有 `ballot`／node／date 條件，
   而抽籤後統計只在抽籤已公告的 node＋date 上被呼叫。同一輪也發現
   `afterstatus=5/8/13`（退件／取消／禁止）沒有統計格是**刻意排除**不是缺漏。
   **拿到一個嚇人的數字時，先確認它的統計範圍等不等於 code 實際查詢的範圍。**

**給接手者的一句話**：這套系統的規則絕大多數在 DB 不在 code，
所以「讀完 code 就知道規則」是錯的；但 DB 裡的值也未必等於機關原文，
兩邊都要對，缺一邊都會做出錯的判斷。

## ⚠ 關於「第 N 列」的引用

`queries.sql` 中的「補對照表第 N 列」是依**產出時的 82 列**編號。
本次回填新增了 6 列，**N 之後的列號已經位移**。
查詢與規則的對應關係請以 `queries.sql` 每條註解的**規則描述文字**為準，不要只看列號。
（下一輪若要固定引用關係，建議先為每列加上不隨編輯變動的 ID。）

**「沒實作」中最值得注意的一組**：所有帶「**時刻**」（15:00、23:00 截止）、「**星期別**」
（週六至翌週一、非假日）、「**同一人同日不得重複**」的規則，一條都沒有實作。
`RuleSet` 只有「天」與「月」兩個欄位，結構上就承載不了這些條件。

**已於 2026-09-08 執行 S1／S2（唯讀）並回填數值。** 仍標「值在DB(待查)」的列，
