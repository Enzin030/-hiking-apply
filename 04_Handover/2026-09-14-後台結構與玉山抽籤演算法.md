# 主題 S　後台不是「一個後台」，是六個 app 加一批排程

### Q91. `NationPark/` 底下是什麼？

  **① 後台 web app（六份，又是複本結構）**

  | 目錄 | 檔數 |

  | `fcwb_admin` | 4,462 |
  | `fcwb_admin_spnp` | 3,589 |
  | `newweb` | 2,977 |
  | `newweb_spnp` | 2,778 |

  合計 17,176 檔。`fcwb_admin` / `fcwb_admin_spnp` 是一組，
  `newweb` / `newweb_spnp` / `newweb_online` 是另一組——
  **前台「三套 code ＋ en/jp 複本」的結構，在後台同樣存在**。
  `_spnp` 後綴與前台的 `spnp_closestart`（雪霸）等欄位同源，
  推測是機關別的分支，**但這是推測，未驗證**。

  **② 排程程式（約 40 個，以中文命名，名稱即用途）**

  名稱本身就是一份功能清單，例如：
  `排程-玉山-長程不抽籤宿營地給號(BookingNodeGetGnum)`、
  `排程-雪霸-每日床營位後補排程`、`排程-雪霸-每日共用床營位遞補排程`、
  `排程-雪霸-檢查是否有超出承載量的宿營地`、`排程-共用-刪除七天草稿資料`、
  `排程-共用-隱碼3年以上個資資料`、`玉山單日往返限額路線自動核准遞補`、
  `雪霸三分之二轉後補`、`雪霸批次退件`、`一站式核准後代送入山`。

  **這解釋了一件事**：前台看不到候補與遞補的實作，是因為那些都在排程裡，
  不在 web app 裡。太魯閣候補另有獨立目錄 `TARKO_Waitinglist`（與 `_2018` 舊版並存）。

  **③ 工具與資料轉換**
  `HtmlPdf`／`htmltopdf`（許可證 PDF，對應 09-11 主題 I 的失效問題）、

  `軟體-pdf產生軟體`、`軟體-無效連結掃描軟體`。

# 主題 T　玉山抽籤演算法（`RulesForDrawingLots.cs`）

`fcwb_admin/App_Code/RulesForDrawingLots.cs`，161,259 bytes／3,031 行。
類別開頭寫死 `unitpark = c951cdcd-...`（玉管處），**這支只管玉山**。

### Q92. 抽籤是純隨機嗎？

- **答**：**不是。基本是隨機，但有一條會改變中籤機率的優先規則。**

  基本盤：參加抽籤的隊伍以 `order by newid()`（SQL Server 隨機）排序。
  篩選條件為 `bollot=1 and ballottype=0 and status in (6,0,3)`，
  且排除 `foreignerresvedplaces='1'`（外籍保留）與 `IsActive='1'`（活動保留）——
  這兩類**已先配好床位，不參加抽籤，直接必中**，只是後續補給序號與狀態。

  **優先規則**：抽**排雲山莊以外**的宿營地時（`if (node_id != cloudhouse)`），
  程式會先撈出「**前幾天已經在圓峰山屋抽中床位**」的隊伍優先處理，
  而且是 `for (day = sumdaymax; day >= 1; day--)`＋`having count(*) = @day`——
  **在圓峰住越多天的隊伍，越早被處理，中籤機率越高**。
  這批隊伍內部仍以 `newid()` 隨機排序。
- **設計意圖（推測）**：降低「多日行程其中一日未中籤者逕予退件」
  （`notice_a1` 抽籤結果）的發生率——前幾天已中的隊伍若後面沒中，整案就作廢。
  **但這是從程式形態推的，原文沒有記載這條優先權。**
- **要問機關**：這條優先規則**機關原文沒有揭露**。
  抽籤的公平性揭露與否是業務決定，不是技術問題。115 案若沿用，要先確認機關認不認這條。
- **出處**：`RulesForDrawingLots.cs:564`（隨機排序）、`:665-700`（優先規則與基數查詢）、
  `:314-334`（外籍保留／活動保留必中）。

### Q93. 又一組寫死的 `node_id`

- **答**：類別欄位直接寫死兩個節點：
  `cloudhouse = "3"`（排雲山莊）、`circlehouse = "4"`（圓峰山屋）。
  另有 `iMaxPcnt = 999`（人數上限哨兵）。
  **抽籤規則因此綁死在這兩個 node_id 上**——若哪天排雲或圓峰的節點資料被重建、
  換了 `node_id`，抽籤會安靜地套用錯誤的規則。
  這與前台 `FiscApi.cs` 寫死 `node_id=3` 取費率是同一個脆弱點，
  也與 09-11 查到的「排雲山莊在 `node` 有三筆同名（3／296／377）」連在一起看。
- **出處**：`RulesForDrawingLots.cs:21-24`。

### Q94. 抽完之後怎麼處理沒中的？

- **答**：程式內有完整的三段落：中籤（`drawOrd` 給序號、狀態轉中籤、
  需繳費的宿營地同時更新 `NEWCANCELNUM`）、床營位滿了轉**候補**
  （並標記「候補即後續的天數不參與抽籤」）、補滿則轉退件（`status=5`，
  該段的註解自己寫著「補滿則??退件?? 5」，**帶著問號，原開發者也不確定**）。
  公告內容同時產中／英／日三版，姓名以「中間加 *」遮罩。
- **出處**：`RulesForDrawingLots.cs:600-660`（中籤）、`:795-900`（候補）、
  `:901-925`（退件與狀態更新）、`:372`／`:773`／`:881`（姓名遮罩）。

# 主題 U　狀態碼：後台與前台**一致**，第 10 題可以結清

### Q95. `status = 17` 到底是「初審完成」還是「備取」？

- **答**：**初審完成。** `mental-model.md` 第 10 題問的是——前台
  `YuShanFun.cs` 同一支檔案裡，`:2251` 稱 17 為「初審完成」、`:2361` 稱「備取」，
  何者為準。後台 `fcwb_admin/App_Code/YushanUtility.cs:537-573` 是**獨立的一份實作**，
  它把 `17` 對到「初審完成」、`12` 對到「備取」。
  **兩份獨立實作一致**，所以前台那處把 17 稱備取是筆誤，不是另一種語意。
- **附帶**：後台把待補件／待繳費**分成三碼**，比前台細：

  | 碼 | 後台名稱 | 前台（`hike_api_code.cs`）|
  |---|---|---|
  | 0 | 中籤 | 中籤 |
  | 1 | 初審完成，待補件 | 併稱「待補件／繳費」 |
  | 9 | 初審完成，待繳費 | 同上 |
  | 10 | 初審完成，待補件&繳費 | 同上 |
  | 3／6／7 | 排隊預約 | 排隊預約 |
  | 11 | 複審完成 | 複審完成 |
  | 12 | 備取 | 備取 |
  | 17 | 初審完成 | 初審完成（另一處誤稱備取）|

  規格若要寫「申請進度」的狀態文案，**應以後台這份為準**，前台是簡化過的。
- **尚未結清**：106 年手冊提到後台把後補分「宿營地不足後補」與「路線承載量不足後補」
  兩種（`mental-model.md` 第 22 題）。這兩個字串在 `fcwb_admin/App_Code` 裡**搜不到**，
  可能在 `.aspx` 樣板、別的 app（`newweb*`），或 9 年來已改名。**這題仍未結清。**
- **出處**：`fcwb_admin/App_Code/YushanUtility.cs:537-573`；
  對照前台 `hike_api_code.cs` 的 `getStatusTitle`（系統概覽第六節）。
