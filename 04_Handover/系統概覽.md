# 00 · 系統概覽 — 這套系統到底在做什麼

> **這是整疊交接文件裡最先讀的一份。** 其他文件（`cases.md`、`rules-vs-code.md`、
> `divergences.md`）都是「哪裡有問題」的清單；讀那些之前，你需要先有一張「它本來
> 長什麼樣」的圖。這份就是那張圖。
>
> 讀法：先把「一~五」讀完，你就有整體輪廓了；「六」以後是各子系統的細節，可以
> 之後按需要回來查。每一節結尾的 `→ 雷` 是指向 `cases.md` / `rules-vs-code.md`
> 對應問題的指標，第一次讀可以先跳過，只留意「這裡有雷」即可。
>
> **一個誠實的前提**：這份文件是從 code 與資料庫實測反推出來的，**沒有原始需求
> 規格書**。所以凡是講「為什麼這樣設計」的地方，多半是推測，會標明；講「系統實際
> 怎麼運作」的地方才是事實。這跟整個分析的限制一致——我們能看到系統做什麼，看不到
> 當年為什麼要它這樣做。

## 一、一句話：這是什麼

一個**登山申請的單一入口網站**。民眾想去台灣的高山（玉山、雪霸、太魯閣三個國家
公園，加上林業署的山屋、警政署的入山證），本來要分別到各機關網站申請；這套系統
把它們收在同一個入口，民眾在這裡填一次表，系統再依機關把案子分流出去。

服務三種人：

- **民眾**（申請人）— 送出登山申請、查進度、繳費、辦理異動或取消。
- **各機關承辦**（玉管處、雪管處、太管處…）— 審核、設定路線與名額、發布封園公告、
  建置違規停權名單。承辦用的是**後台**（`manasystem/`、`NationPark/`），本次分析
  幾乎沒讀，所以後台的事這份講得很淺。
- **外部系統** — 有些山屋（嘉明湖、天池、九九山莊…）不歸這套系統管，這裡只負責把
  申請透過 API 轉送過去。

**第一個要建立的心智模型**：這不是「一套系統服務三家機關」，而是**三套各自獨立的
程式，勉強共用一個入口頁**。這一點會反覆解釋你後面看到的所有怪事，先記住它。
（詳見第四節）

## 二、核心名詞（先認得這幾個，後面才讀得懂）

看 code 和其他文件時，這幾個詞會不斷出現。先建立最低限度的認識：

| 名詞 | 白話 | 對應資料表 |
|---|---|---|
| **機關（Org）** | 玉山／雪霸／太魯閣／林業署／警政署，各有一個 GUID | `EIP_Core_Organization` |
| **主路線 / 次路線** | 民眾選的登山路線。主路線是大分類，次路線是實際申請單位 | `Fixedclimbmain` / `Fixedclimb` |
| **宿營地點（node）** | 路線上會住宿或經過的點：山屋、營地、登山口、山峰 | `node` |
| **RuleSet** | 「機關層級」的規則設定：期限幾天、人數上下限、封園日… | `RuleSet` |
| **申請案（applylist）** | 一筆申請。它有一個 `status`（狀態碼）標示走到哪一步 | `applylist` |
| **抽籤 / 候補** | 熱門路線名額不足時的兩種處理機制（下面第五節詳解） | `booking`、`ballot` |
| **同意書條文（attention）** | 申請前要勾的注意事項 | `attention` |
| **違規停權名單** | 被停權者在停權期間不能申請 | `tb_Blacklist` |

**一個關鍵認知**：這套系統的規則**絕大多數不寫在 code 裡，而在資料庫的欄位值裡**。
`RuleSet` 的一個數字改了，全站的期限就變了。所以「讀完 code 就懂規則」是錯的——
code 只告訴你「它去讀哪個欄位」，欄位裡裝什麼要連 DB 才知道。這是這份交接最重要的
一句話，`rules-vs-code.md` 整份都在處理這件事。

## 三、一個申請案的一生（主線流程）

這是整個系統的骨幹。一個民眾從點進網站到送出申請，走過的頁面是這條線：

```
apply_1 ──▶ apply_1_2 ──▶ apply_1_4 / _1_3 / _1_5 ──▶ (送出) ──▶ 抽籤或候補 ──▶ 核准 ──▶ 入園 ──▶ 結案
 選機關      同意條文        填申請表（三家各一支）
 選路線                     ├ 玉山 apply_1_4
                           ├ 雪霸 apply_1_3
                           └ 太魯閣 apply_1_5
```

一步一步看它在做什麼：

**① `apply_1` — 選機關、選路線**
民眾進來第一頁。系統從資料庫撈出各機關、各路線列給你選。機關按鈕是動態產生的，
路線清單依你選的機關過濾。
`→ 雷`：機關分派這裡用 GUID，下一頁卻改用「機關名稱是否含『玉山』」字串比對，
兩把鑰匙不一致（cases Q9–Q11、rules 第 20 列）。玉山路線在「全部」和「玉管處」
兩種篩選下數量可能不同（cases Q12）。

**② `apply_1_2` — 同意條文**
顯示該機關的注意事項（`attention` 表），民眾勾選後按「同意，下一步」。
`→ 雷`：這是全系統最需要注意的一個弱點。前端會檢查有沒有勾，但**後端根本沒讀
勾選結果、也不存任何同意紀錄**——停用 JavaScript 或直接送出就能跳過（cases Q7）。
而且部分條文預設就是勾好的（cases Q8）。

**③ `apply_1_4` / `apply_1_3` / `apply_1_5` — 填申請表**
依機關進入三支**不同**的申請表程式（玉山／雪霸／太魯閣）。填隊伍成員、路線、
日期，系統在這裡做各種檢查：人數上下限、期限、年齡、封園日、黑名單…
`→ 雷`：這三支是各自獨立的 code，同一種檢查在三家可能寫法不同、結果不同。
這一步是「不一致」類問題最密集的地方。

**④ 送出之後 — 抽籤或候補**
熱門路線（需要抽籤的）進入抽籤流程；額滿的進候補。不需要抽籤的路線直接往下。
（第五節詳解）

**⑤ 之後 — 核准 → 入園 → 結案**
案子的 `status` 一路變化：排隊預約 → 中籤 → 待補件/繳費 → 核准入園 → …
這些狀態碼是理解後台統計的關鍵，第六節有完整對照表。

**⚠ 貫穿整條線的一個真相：整個流程沒有「登入」。**
你不會在任何一步看到帳號密碼。系統靠什麼確保你是照順序走過來的？靠檢查
「你上一頁是不是從 `apply_1_2` 來的」（HTTP Referer 標頭）。這個標頭可以偽造，
而且正常使用者若關掉 Referer 反而會被擋。這是整個系統安全模型的地基，
務必先知道（cases Q1–Q6）。

## 四、為什麼是「三套 code」（這點解釋一切）

前面說過，這不是一套系統服務三家，是三套程式共用入口。具體長這樣：

| 機關 | 申請表主程式 | 規則邏輯放哪 |
|---|---|---|
| 玉山 | `apply_1_4` | `App_code/YuShanFun.cs` |
| 雪霸 | `apply_1_3` | 規則直接內嵌在頁面裡 |
| 太魯閣 | `apply_1_5` | `tarokoapplyControl/` + `App_code/taroko/` |

而且**每一套又各自有 `en/`（英文）和 `jp/`（日文）的完整複本**——不是語系資源檔，
是整套 code 複製三份。所以實際上有將近九套平行的程式碼。

這一點是後面所有怪事的根源，記住它你就能預測很多問題：

- **同一條規則，三家可能實作不同**。例如「什麼算長程縱走」，太魯閣只看一個欄位、
  雪霸卻用兩套節點推導（rules 第 193 列）。
- **改一個地方不會全站生效**。修了玉山的邏輯，雪霸、太魯閣、還有 en/jp 六份複本
  都不會跟著動。
- **複本會漂移**。中文站改了、英文站忘了改，兩邊行為就不一樣（例如大小寫處理，
  cases Q4）。
- **新增一家機關要改 code**，不是改設定（cases Q11）。

**推測（非事實）**：這種結構通常是「先做好一家、後面兩家用複製貼上改出來」的產物。
但沒有需求文件佐證，這只是從 code 形態推的。

## 五、名額怎麼分：抽籤、候補、承載量

「名額」是登山申請系統的核心，但它在這套系統裡**不是一套機制，是三套**——又是
三家各做各的：

- **玉山：抽籤 + 備取 + 遞補**。熱門路線在入園前約一個月抽籤，抽完有中籤、備取、
  可遞補等狀態。抽籤時段設定在 `ApplyBanTimeMuti` 表。
- **太魯閣：排程驅動的候補**。不是抽籤，是候補排隊，由背景排程處理，每條路線每日
  有候補名額上限。
- ~~**雪霸：兩者都沒有**。程式裡完全找不到候補/遞補的實作。所以「三家都有候補」是
  錯的認知（rules 第四節末列）。~~
  **更正（2026-09-18）**：上句只掃了 `SheipaWebService.cs`。雪霸申請頁 `apply_1_3.aspx.cs` 有**送件當下即時判定的候補**：
  任一晚承載量不足即整件轉候補（`status = 3`），另有後補額度 `RuleSet.bakroomnum`／`bakcampnum`，超過即擋下送件。
  **三家都有額滿後的處理，只是機制不同**（玉山抽籤、太魯閣排程候補、雪霸即時候補）。
  雪霸「遞補」（有人取消後候補者補上）的實作仍未找到，`[待確認]`。詳見 `cases.md` Q33 2026-09-18 17:10 更正。

**承載量**（一個宿營地每天能容納多少人）存在 `node` 表，而且分三組欄位，由該點的
`roomtype` 決定用哪一組：

| roomtype | 這個點是 | 用哪組承載量欄位 |
|---|---|---|
| 0 | 山屋（算床位） | `generalnum` / `holidaynum` |
| 1 | 營地（算營位） | `generalnumt` / `holidaynumt`（t = tent） |
| 2 | 山屋+營地並存 | 兩組都用 |
| NULL | 非住宿點（登山口、山峰） | 三組都空 |

`→ 雷`：床位/營位是由另一個欄位 `bedtype`（0/1）分流寫進去的，而 `bedtype` 的
0 到底是床還是營，code 內部前後一致但**從未被外部驗證**。如果 0/1 其實相反，
所有山屋床位數與營位數會整組算反——這是目前最大的未解技術疑點
（rules「六件事」第 7 點）。

`→ 雷`：取承載量最大值時要小心，資料裡有 999/9999/99999 這種「無上限」哨兵值
（自備搭帳、避難小屋等不限量的點），直接取 MAX 會拿到荒謬數字
（rules 第七節段首）。

## 六、狀態碼對照表（讀懂後台統計的鑰匙）

申請案的 `status` 和抽籤後的 `afterstatus` 是一堆數字，這張表是全系統唯一把它們
寫全的地方（來自 `hike_api_code.cs` 的 `getStatusTitle`）。看任何跟「案件統計」
有關的東西都需要它：

| 碼 | 意義 |
|---|---|
| 0 | 中籤 |
| 3, 6, 7 | 排隊預約 |
| 1, 9, 10 | 待補件 / 繳費 |
| 4 | 核准入園 |
| 5 | 退件 |
| 8 | 取消入園 |
| 11 | 複審完成 |
| 12 | 備取 |
| 13 | 禁止入園 |
| 17 | 初審完成（**注意：同一支檔案裡另一處把 17 稱作「備取」，命名衝突**）|

`→ 雷`：`afterstatus` 為 NULL 代表「還沒有抽籤後狀態 = 排隊預約」，**不是遺漏值**。
分析初期曾誤把上百萬筆 NULL 當成「案件從統計中消失」，後來證實那是正常口徑
（全表計數含了不抽籤、未公告的案件）。這個教訓本身值得記：**拿全表計數去對
階段性統計，數字會對不上但不代表有 bug**（cases Q36、rules 第四節）。

## 七、規則到底放在哪（一張定位圖）

接手後最常見的任務是「某條規則在哪裡改」。這套系統的規則散在四個地方，這是最容易
迷路的部分：

| 規則類型 | 放在哪 | 舉例 |
|---|---|---|
| 機關層級的數值 | `RuleSet` 表 | 申請期限幾天、人數上下限、取消天數、封園日 |
| 路線層級的數值 | `Fixedclimb` 表 | 某條路線自訂的期限、人數（會覆寫機關預設）|
| 承載量 / 費用 | `node` 表 | 每個宿營地的床位數、規費 |
| 完整的文字敘述 | 機關原文（`notice_*`、`attention`）| 給民眾看的規則全文 |
| **寫死在 code 裡** | `.cs` 檔 | 少數，通常是問題所在（下面） |

**沒有任何一個地方有「完整的規則」**——要拼四塊才看得到全貌。這是為什麼接手會覺得
亂：你在 code 裡找規則，但規則多半不在 code 裡。

`→ 雷`：少數規則寫死在 code，這幾乎都是問題來源——寫死的封園日期過期了不報錯
（rules 第十一節）、玉山「5 天」有一半讀 DB 一半寫死（rules 第一節第 3 列）、
太魯閣共同承載量的路線 ID 寫死在程式（rules 第四節）。看到 code 裡有寫死的
數字或日期，先當它是可疑的。

## 八、承辦端與外部依賴（本次分析的盲區）

誠實標記這份文件最弱的兩塊，接手時要知道這裡資料最少：

**承辦後台**（`manasystem/`、`NationPark/` 共約兩萬檔）本次幾乎沒讀。所以：
審核流程、名額怎麼在後台調整、抽籤程序本身怎麼跑、封園公告怎麼發——這些都只知道
「前台會去讀後台建立的資料」，不知道後台怎麼建。**抽籤的實際演算法在後台，前台
只看得到抽完的結果。**

**外部系統**：嘉明湖、天池山莊、檜谷山莊等林業署山屋不歸這套系統管，這裡只透過
`web.config` 裡的 API URL 轉送。這些的規則、名額、費用都在對方系統，本機資料庫
沒有。唯一例外是九九山莊——原文寫「請至一站式服務網申請」，系統也確實有對接程式碼。

**繳費 / 退費 / 異動**（`apply_2`、`apply_4`、`apply_5`、`FiscApi.cs`）本次未讀。
如果你接手的範圍含金流，這幾支是還沒被分析的區域。

**一句話帶走**：這套系統的規則絕大多數在資料庫、不在 code；而資料庫裡的值又未必
等於機關公告的原文。接手做任何判斷，code、DB、原文三邊都要對，缺一邊都會錯。
